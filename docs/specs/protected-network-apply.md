# 规格：限时确认的本机配置应用

## 状态、目标与授权

用户已授权按安全默认方案自主推进，不再逐项等待确认。实现与测试仍不在当前生产主机
注册恢复服务、替换安装版、重启 Mihomo/networkd 或重启整机；不自动推送 GitHub。

为通过 SSH 使用的 Linux 提供显式“保护应用”：新配置试运行后须限时人工确认，
未确认则恢复独立的已知可工作基线。恢复任务不能依赖 TUI 或 SSH 会话存活。
API/GitHub 请求成功不能自动确认，也不能当作 SSH 安全证明。

## 范围与前提

- 保留普通 `p`，新增大写 `P` 保护应用及 `network` 命令组。
- 仅本机规范路径 `/etc/mihomo-tui/config.yaml` 和现有受管理的 `mihomo.service`。
- 服务须已 active、enabled，并读取规范配置；核心和服务绑定在试运行期间不得改变。
- 外部 Controller、自定义配置路径、缺失/未启动服务均不得触发本机保护应用。
- 首个基线必须由管理员明确确认“当前磁盘配置已加载且网络可用”，不能用编辑备份冒充。
- 基线绑定核心文件身份和有效服务配置；绑定变化后必须重新人工建立基线。
- 首版候选只允许修改 `tun` 和 `dns`，其余原生 YAML 内容须与基线语义相同。
  不快照整个数据目录；拒绝新增/修改 provider、代理、规则及其路径，避免候选改写基线依赖。
- 默认确认窗口 90 秒，可选 30–300 秒；计时不依赖可被 NTP 修改的墙上时钟。
- 不改 networkd、物理接口、系统 DNS、订阅缓存或节点选择；不安装或升级核心。
- 不新增 Cargo 依赖，不改 CI；所有真实特权动作只会在使用新功能时显式发生。

## 用户接口

```bash
sudo mihomo-tui network status
sudo mihomo-tui network checkpoint --confirm-working
sudo mihomo-tui network apply --confirm-within 90
sudo mihomo-tui network confirm TRANSACTION_ID
sudo mihomo-tui network rollback TRANSACTION_ID
```

`checkpoint` 的人工声明不可由普通启动或探测隐式代替。初始化保护设施会写入私有恢复
工作程序、systemd 恢复 timer/service 和独立启动前检查 drop-in，但不会重启核心。
`status` 只读，不初始化目录或服务。

TUI 的 `P` 使用同一事务引擎；界面显示事务 ID、剩余时间、确认与立即恢复入口。
确认须明确表示已检查新 SSH 会话/所需网络；普通退出或断线不会自动确认或取消保护。
操作等待均在后台，避免让恢复相关系统命令阻塞终端。

## 持久化与状态机

- `/var/lib/mihomo-tui/network-guard/` 为 root 私有目录，目录 `0700`、数据文件 `0600`。
- 已知基线、候选内容为独立不可变快照；只保存派生 ID 和 SHA-256 引用，不接受任意路径。
- 全局账本一次原子写入同时记录当前基线与事务阶段，文件及父目录均 fsync。
- 确认时基线引用和事务终态一起提交；回滚始终使用该事务自己的基线，不使用后来变化的指针。
- 阶段至少区分 armed、trial、rolling_back、confirmed、rolled_back、conflict、recovery_failed。
- 一个时刻只允许一个未解决事务。旧 ID、旧确认或过期任务不能作用于新事务或已确认事务。
- 私有配置和日志原文不出现在状态输出、命令行、systemd unit 或 Git 仓库中。
- 快照、账本、外部命令输出和重试次数有上限；仅清理可确定不再被账本引用的本功能快照。

## 保护与恢复顺序

1. 检查 root、已有基线、核心/服务绑定、配置权限和语义；失败不得重启核心。
2. 准备并同步候选快照。先启动、启用并验证独立恢复 timer，再发布待确认账本。
3. 账本持久化后才请求核心重启；人工窗口内不长期持有运行时锁。
4. 确认在运行时锁内重新检查：ID、阶段、boot ID、未过期、候选哈希、服务/核心绑定，
   并确认核心已经进入不同于应用前的活跃 InvocationID。不能只因旧核心仍 active 就确认。
5. 超时或明确请求恢复后，先持久化 rolling_back，再以保留被替换文件的方式安装基线，
   fsync 文件和配置目录后请求重启。安装采用同目录捕获旧文件与不覆盖发布，避免盲目覆盖新编辑。
   两步之间可能短暂缺少规范路径；启动前检查必须阻止核心在此时读取候选/缺失配置。
6. 恢复文件、服务重启、恢复完成分开记录。中途退出可重试；失败不能标成恢复成功。
   恢复必须保存独立于“应用前 InvocationID”的重启凭据：基线耐久安装后记录当前调用 ID，
   再请求重启，并等待不同且活跃的调用。InvocationID 不是可排序的计数器。
   开机 hook 则记录该次待启动的确切调用 ID，之后须看到同一调用真正 active，不能用空值
   充当证据；hook 只恢复文件，不提前记录服务恢复完成。
7. 恢复命令须限时、重试有界。已确认/已恢复的任务不会再被旧 timer 覆盖。

### 进程退出、开机与 systemd

恢复工作程序具有独立、稳定、root 所有的私有副本，不依赖仓库或安装版二进制之后的位置。
事务未结束时不能替换它。timer 使用持久 unit 文件，不把 `/run` 下 transient unit 当作重启保障。
每次保护应用前检查 helper 的协议和文件 SHA-256 必须与当前程序匹配，并实际运行一次恢复
unit 的无待处理事务路径。首次挂接 hook 前先验证 ELF 可执行和 unit 可运行，避免 noexec
目录先引入不可用的启动依赖。首版不跨构建替换已挂接的 helper；设施换代须维护部署与重新
验收。未挂接、无未解决事务的初始化修复才允许停止旧 timer/工作进程后持锁替换。

使用 boot ID 加 `/proc/uptime` 的期限判断；开机发现未确认的旧 boot 事务时应恢复基线，
不重新发放 90 秒试运行。独立 `ExecStartPre` 检查必须在 Mihomo 读取配置前完成恢复，
且自身不能启动/重启 `mihomo.service`，避免启动顺序死锁。
没有未解决事务时的 hook 必须无锁、只读地返回；普通应用/内核升级持锁时也能正常启动。
工作程序单次执行有明确 TimeoutStartSec/TimeoutStopSec，不使用 RemainAfterExit，
不在一次 oneshot 中无限等待，进度持久化后交给下一次 timer 接续。

普通 timer 以约 5 秒检查间隔执行；不是精确 90 秒强制恢复承诺，还受调度、锁和服务
启动耗时影响。`Persistent=true` 只适用于 OnCalendar，不能用它弥补 monotonic timer 的重启。
不能从持有应用锁的路径同步等待一个又要获取同一锁的启动前工作程序。

### 并发与外部变更

普通应用、规范配置写入、核心升级及恢复共享同一个运行时锁。事务未解决时，合作的
TUI/CLI 拒绝新的本机写入、普通应用和升级；只读页面继续可用。

配置若已被其他编辑器/旧二进制改成既不是候选也不是基线的内容，自动恢复进入 conflict，
不覆盖后续编辑；需要人工处理。同样，核心或服务绑定改变不能被静默接受。这个边界意味着
不能保证在外部干预、磁盘损坏、核心被卸载或恢复服务被禁用后仍能恢复 SSH。
严格互斥保证只适用于合作的写入者；不持锁的 root 编辑器仍可能与检查/替换竞争。
恢复会保留实际移走的文件，发布新规范路径时不覆盖已由其他写入者创建的文件；若检测到
竞态则记录冲突并保留所有可识别内容，不承诺与不合作的原地写入实现全局文件系统事务。

快照文件与快照目录项必须先耐久化，账本才能引用它；规范配置的内容及重命名/链接目录项
必须先 fsync，账本才能进入 rolled_back。内存中的哈希匹配不能代替断电耐久性顺序。

## 结构与风格

```text
src/network_guard/       事务模型、私有存储、系统接线、测试
src/runtime/             原子应用入口、受管理 unit/drop-in 识别
src/config.rs            规范配置写入的互斥与事务检查
src/core_upgrade/        升级前拒绝未解决事务
src/main.rs              network 子命令与内部恢复入口
src/app.rs               P、倒计时与显式确认/恢复交互
docs/server-guide.md     初始化、应用、恢复及故障处理
```

沿用 Rust 2024、显式 `Result`、中文提示、snake_case 和 serde 类型。
使用阶段枚举和不可变快照引用，不通过提示文案推断状态。例如现有锁接口：

```rust
pub fn acquire_runtime_lock() -> Result<RuntimeLock, String>
```

锁必须在所有检查和状态更改之间持续持有；后台任务重新取得锁后重新读账本，不能使用旧缓存。
新增模块只封装本功能，不引入通用工作流框架。

### 首轮审阅处理

启动锁冲突、跨文件耐久性、恢复专用 InvocationID 凭据、跨核心基线失效、共享 provider
依赖、oneshot 执行上限、旧 helper 协议兼容均为有效且可操作问题，以上约束已修正。
不合作外部写入无法由应用锁覆盖属于有效边界限制：收窄保证，并保留被移走内容、使用
不覆盖发布来降低风险。用户已授权自主决策，本轮不追加外部模型 CLI 审阅。

后续两轮审阅另外修正了文件元数据与打开句柄不一致、损坏调用 ID 被当成激活证据、未知
托管 drop-in 被覆盖、检查错误未落账、恢复调用链逃逸到无超时探测等问题。
读取/同步使用同一受检描述符，Linux O_NOFOLLOW/O_NONBLOCK 拒绝符号链接与 FIFO 替换；
账本增加完整性封装和严格 boot/InvocationID 校验。启动激活凭据与重启前凭据明确区分。
worker 只使用有界 systemd 查询和文件身份检查，不进入原库存/版本探测的无界子进程路径。
已完成三轮独立审阅；剩余验证以回归测试与隔离验收为准，不声称已通过真实重启验证。
